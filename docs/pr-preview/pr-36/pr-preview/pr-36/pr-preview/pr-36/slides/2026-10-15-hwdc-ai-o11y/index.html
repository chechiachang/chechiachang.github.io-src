用數據決策，避免 FOMO

  • 把每個工具都試用一遍
  • 閱讀專家的分享與供應商的文章
  • 採用代理商或公有雲的推薦

每個都試用的確是一種選擇，但不太實際；團隊產出會大打折扣，也可能因此失去信心

Step 1｜Baseline 與第一次優化
  • 先理解 CLI 行為
    • Copilot、Codex、OpenCode 各不同
  • 停用不必要的 Tools
    • Copilot 內建 50+ 個 Tools
    • 實務上只用 10+ 個
    • VSCode Extension 也可能增加 Tools
  • 透過 AI Gateway 增加控制點

控制你的 Coding Agent

  • User: “hi”

  • Agent: “Hi! How can I help you today?”

  • 這個簡單的互動就用了 20,000+ Input Tokens

  • 成本約 0.1 USD（3 TWD；$5.00/1M Tokens）

Step 1｜第一次優化成果
  • Token Overhead：20,000+ → 1,000+
  • 成本：$0.10 → $0.005（降至約 5%）
  • 降低進入 Long Context 的機率
    • ≥272K Tokens 價格翻倍
  • 把 Context Window 留給真正有用的內容

OpenAI API Pricing

Input Token Cache 只是折扣，不是免費；它可以改善 Model 在 Long Context 下的效能， 但不該因此被拿來浪費

Step 2｜LLM-as-a-Judge
  • 依 Tracing Metadata 優化成本
  • 依 Input / Output 優化品質
  • LLM 評估輸出品質
  • 傳統測試難涵蓋多變情境

使用 Langfuse 收集 Tracing 資料， 先把 Input/Output 的品質量化， 再使用內建的 Evaluator Library，或自行撰寫 Prompt 評估品質

Step 2｜Observation 評估
  • 評估每次 API Call
  • 看 Input、Output 與 Metadata
  • 小範圍量化，觀察局部品質
  • 不代表 Project 整體品質
  • 從局部分析錯誤類型，找出改進方向
Step 2｜根據評估結果優化
  • 依 LLM-as-a-Judge 結果持續調整
  • 控制變因：
    • Token Usage、Latency、Cost
    • Model Version
  • 調整 Prompt / Instruction
  • 改善 Input / Output 品質

控制變因、調整變因，提升局部評分

Step 2｜Multi-turn Agent

Long-running Agent 不能只看最終答案：

Input: 更新 README.md
讀取 → Plan → Apply Patch → 完成
Output: README.md 修改成功

改評估單一步驟
例如 Plan 或 Apply Patch

Step 3｜Dataset & Experiment

Dataset｜真實工作考題 從 Daily Work Tracing 整理

Input：真實工作需求
Output：Model 的回答
Judge Score：回答品質

Experiment｜同一份考題 控制變因，重複執行

Model：5.4 → 5.5
Tools / Instruction：改動前後

這是使用 Spec-kit 產生的 YouBike API app

Step 3｜整理 Dataset
  • Plan：Context Precision
  • Coding：Answer Correctness
  • 依 Judge 分數分類
  • 高品質案例作為改進參考

注意：從 O11y 走進 Dataset，是個大坑

Step 3｜Data Preprocessing
  • 清理 Tracing 格式，挑選所需 Features
  • 例如 Output.tool_calls.args
  • 記錄呼叫哪些 Tools、帶哪些參數
  • 用 Langfuse SDK 轉換格式
  • Partition Dataset

持久化儲存，作為測試題庫

Step 3｜第三次優化：選擇最佳工具
  • 用題庫測試不同選項：
    • Model：Pro、Mini、Nano
    • Model 版本：GPT-5.4、GPT-5.5
    • Thinking Effort
    • Agent：Codex、OpenCode、Copilot
  • 不必等 Model 變強才解決問題
  • 選適合的工具，平衡品質與成本
Step 3｜Evaluation → Cost Estimate
  • 測試題數與使用的 Model
  • LLM API Metrics、Token 用量
  • Quality Estimate

沒有測試基礎的預算，只是市場喊價

Step 0｜先釐清需求

需求應該先釐清

許多團隊卻先討論要不要換工具：

  • 需求還不清楚
  • 成員對 LLM 的理解有落差

先建立監測，讓團隊看見數據

用數據調整認知，讓討論回到現實

不能怪團隊不理解成本；要先讓大家容易看見成本，才會開始在意成本

Step 0｜Coding Agent 效率

想提升團隊效率，先定義「效率」：

$$ \text{Overall Efficiency} = \frac{\text{產出數量} \times \text{產出品質}}{\text{Token Cost} \times \text{花費時間}} $$

降低 Cost、Latency、Error Rate
控制 Context Window
提升 Output Quality

Step 0｜從需求走向 Action

依任務選工具：

  • Model：
    • Mini、Nano
    • Low Latency、Low Error Rate
  • Gateway Routing：
    • AgentGateway
    • LiteLLM
  • Context Management：rtk
  • Greenfield：Spec-kit
Step 0｜讓團隊 On the Same Page
  • Dev Team：Chargeback
  • 選擇 Model 與 Tool
  • 與 Stakeholders、管理者對齊期待
  • 量化效能指標：
    • 正確率、Error Rate
    • Latency、Cost
  • 有 AI，不代表產出就能提升十倍

有 Evaluation 後，可以說：

產出約提升 2–3 倍，數據在此
